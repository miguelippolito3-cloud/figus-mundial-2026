🗺️ ¿Qué vas a aprender con esta guía?

En esta sesión de trabajo, vos aportaste el problema y los materiales (fotos del álbum, listas manuscritas, el formato deseado) y yo —Claude, una IA— lo transformé en una aplicación web completa, publicada en internet, sin que vos escribieras una sola línea de código.

Esta guía explica cada decisión y cada tecnología involucrada, con el lenguaje técnico correcto y una explicación de por qué se usa. Al terminar vas a entender el proceso completo, desde el pedido hasta la URL pública.

No necesitás saber programar para entender esto. Solo necesitás la curiosidad que ya tenés.

Fase 1 — Entender el problema

📸 El Prompt y la Visión Artificial

Todo empezó cuando me mandaste las fotos y me describiste qué querías. Eso se llama prompt: la instrucción que le das a una IA. La calidad del resultado depende enormemente de qué tan bien describís el problema.

Junto con el texto, mandaste 5 imágenes: el índice del álbum, 3 páginas de listas manuscritas y una foto del álbum abierto. Yo no "vi" esas fotos como las ve un humano —las analicé píxel a píxel usando un modelo de visión por computadora entrenado para entender imágenes.

Esto me permitió leer las abreviaturas de los países (MEX, RSA, KOR…), identificar los números de figuritas que estaban escritos a mano con marcador, y entender la estructura del álbum aunque la escritura era irregular y había tachones.

Conceptos clave
Prompt / Prompt Engineering
Instrucción / Ingeniería de instrucciones
El texto que le escribís a la IA para pedirle algo. "Prompt engineering" es el arte de redactar ese pedido de forma que la IA lo entienda bien y dé el mejor resultado posible.
Computer Vision
Visión por computadora
Capacidad de una IA de analizar e interpretar imágenes. No "ve" como un humano; convierte la imagen en millones de números y aplica modelos matemáticos para entender qué hay en ella.
Multimodal AI
IA multimodal
Una IA que puede procesar distintos tipos de datos al mismo tiempo: texto, imágenes, audio. Claude es multimodal: procesó tus fotos Y tu texto en el mismo pedido.
Context Window
Ventana de contexto
La "memoria de trabajo" de la IA en cada conversación. Todo lo que mandás —texto, imágenes, código— ocupa espacio en esta ventana. Si se llena, la IA empieza a "olvidar" lo anterior.
🧠
La analogía Imaginate contratar un asistente brillante que nunca trabajó con vos antes. Cuanto más claro le explicás el proyecto —qué es un álbum de figuritas, para qué sirve, qué querés al final— mejor va a ser su trabajo. El prompt es exactamente eso: el brief inicial que define todo lo que sigue.
Lo que hice en este paso
  • Leí las 5 imágenes que mandaste usando visión por computadora
  • Extraje la lista de los 51 equipos con sus abreviaturas
  • Identifiqué la estructura: FWC (sección especial), 48 selecciones × 20 figuritas, sección CC
  • Interpreté el formato de exportación que mostraste como ejemplo
  • Entendí que el estado inicial de Mike venía en las listas manuscritas

Fase 1 — Diseño de la solución

🏗️ Elegir la tecnología correcta

Antes de escribir una sola línea de código, la decisión más importante es qué tecnología usar. Esta decisión tiene consecuencias enormes: afecta el costo, la complejidad, la velocidad de desarrollo y cómo se usa la app.

Para este caso, elegí una aplicación web estática: un único archivo HTML que funciona directo en el navegador, sin servidor propio, sin base de datos en la nube, sin instalación. Es el equivalente informático de un documento Word muy inteligente que el navegador puede abrir.

Conceptos clave
Static Site / Static App
Sitio / App estático/a
Una app que consiste solo en archivos (HTML, CSS, JS) que el navegador descarga y ejecuta localmente. No necesita un servidor procesando pedidos en tiempo real. Simple, rápida y muy barata de alojar.
Dynamic Site
Sitio dinámico
Una app que tiene un servidor procesando datos en tiempo real (PHP, Python, Node.js…). Necesaria cuando hay usuarios, bases de datos compartidas, pagos, etc. Más compleja y cara. No la necesitábamos acá.
Browser / Navegador
Navegador web
Chrome, Firefox, Safari, Edge. Mucho más que un "visor de páginas": es un entorno completo de ejecución de código. Puede ejecutar lógica, guardar datos localmente y manejar interfaces complejas.
No-backend / Serverless
Sin servidor propio
Arquitectura donde toda la lógica corre en el navegador del usuario, sin que vos pagues ni mantengas un servidor. Ideal para apps personales o familiares sin requisitos de datos compartidos en tiempo real.
🤔 ¿Por qué no usamos otras opciones?
  • App móvil nativa (iOS/Android): requiere publicar en las tiendas, pagar cuentas de desarrollador, y los usuarios deben instalarla. Demasiado overhead para este caso.
  • Excel/Google Sheets: no permite la interactividad visual (clicks en números, cambio de colores), ni el layout de impresión compacto que necesitábamos.
  • App con base de datos (Firebase, Supabase…): necesaria solo si los datos se comparten entre dispositivos en tiempo real. Aquí cada quien tiene su control independiente.
  • HTML estático ✅: funciona offline, abre en cualquier celular sin instalar nada, es gratuito de hospedar, y el navegador ya tiene todo lo que necesitamos.
🏠
La analogía La diferencia entre un sitio estático y uno dinámico es como la diferencia entre un libro y un restaurante. El libro tiene todo el contenido dentro: lo abrís y está ahí. El restaurante necesita cocineros, ingredientes frescos y personal en tiempo real. Para leer un libro no necesitás un restaurante.

Fase 2 — Construcción

🎨 HTML, CSS y JavaScript: los tres lenguajes del navegador

Cualquier página web que abrís en tu navegador está construida con exactamente tres lenguajes. Siempre. Son los únicos lenguajes que el navegador entiende de forma nativa, y cada uno tiene una función específica.

No son lenguajes de programación en el sentido tradicional —o al menos, no todos—. Es mejor pensarlos como tres capas de una misma torta, cada una con su rol.

Los tres lenguajes del navegador
HTML — HyperText Markup Language
Lenguaje de Marcado de Hipertexto
Define QUÉ hay en la página: botones, textos, imágenes, divisiones. Es la estructura. Sin HTML no hay nada que mostrar. Creado en 1991 por Tim Berners-Lee, inventor de la web.
CSS — Cascading Style Sheets
Hojas de Estilo en Cascada
Define CÓMO se ve lo que hay: colores, tamaños, posiciones, animaciones. Sin CSS, todo sería texto negro sobre fondo blanco. El "cascading" significa que las reglas se heredan de padres a hijos.
JavaScript
JavaScript (sin traducción)
Define QUÉ HACE la página: responde a clicks, guarda datos, actualiza contenido sin recargar. Es el único lenguaje de programación real de los tres. A pesar del nombre, no tiene nada que ver con Java.
🏗️
La analogía del edificio HTML son los planos y la estructura: dónde van las paredes, las puertas, las ventanas.
CSS es el diseño de interiores: los colores, los materiales, la decoración.
JavaScript es la electricidad, la plomería y la domótica: lo que hace que el edificio funcione, responda y reaccione.
Ejemplo real de la app
<button class="stk miss" data-sec="MEX" data-n="6">6</button> /* CSS: el botón rojo que dice "falta" */ .stk.miss { background: #fee2e2; /* rojo claro */ color: #b91c1c; border: 1.5px solid #fca5a5; } // JavaScript: cuando hacés click, suma 1 al contador counts["MEX"]["6"]++; // de 0 (falta) a 1 (tengo)
Lo que hice en este paso
  • Escribí ~500 líneas de HTML para la estructura de todas las tarjetas de equipos
  • Escribí ~300 líneas de CSS para los tres estados visuales (rojo/verde/amarillo) y el layout de impresión
  • Escribí ~400 líneas de JavaScript para toda la lógica (clicks, cálculos, export, usuarios)
  • Todo en un único archivo .html: la ventaja es que no hay que instalar nada

Fase 2 — Construcción

💾 Guardar los datos: JSON y localStorage

Una app que no guarda datos no sirve de nada. Cada vez que marcás una figurita, ese dato tiene que persistir: si cerrás el navegador y lo volvés a abrir, todo tiene que estar como lo dejaste.

Para esto usamos dos tecnologías que trabajan juntas: JSON (el formato para representar los datos) y localStorage (el lugar donde el navegador los guarda en tu dispositivo).

Conceptos clave
JSON — JavaScript Object Notation
Notación de Objetos de JavaScript
Un formato de texto para representar datos estructurados. Es lo que usa internet para que los programas se comuniquen. Legible por humanos y por máquinas. Se usa en absolutamente todas las apps modernas.
localStorage
Almacenamiento local del navegador
Una pequeña base de datos que cada navegador mantiene en tu dispositivo, por sitio web. Es privada (nadie puede accederla remotamente), persiste entre sesiones, y tiene capacidad de ~5MB. Perfecta para este tipo de app.
Data Structure
Estructura de datos
La manera en que organizamos los datos en memoria para que sean fáciles de leer y modificar. Un mal diseño de estructura de datos puede hacer que un programa simple se vuelva imposible de mantener.
Persistence
Persistencia
La propiedad de un dato de "sobrevivir" aunque el programa se cierre. Sin persistencia, cada vez que cerrás el navegador perdés todo. localStorage da persistencia sin necesitar una base de datos externa.
Cómo se ven los datos guardados
// Así guardamos el estado del álbum de Mike en localStorage: { "MEX": { "1": 1, // figurita 1 de México: la tengo (1) "6": 0, // figurita 6: me falta (0) "7": 2, // figurita 7: tengo 2 (repetida) }, "ARG": { "1": 1, "17": 0, // solo falta la 17 de Argentina ... } }
📒
La analogía localStorage es como la memoria del navegador para ese sitio específico. Es como si tu navegador tuviera una libreta por cada sitio web que visitás. Cuando abrís la app, lee la libreta; cuando hacés un cambio, escribe en ella. Nadie más puede ver esa libreta —ni yo, ni GitHub, ni ningún servidor.
🤔 Implicación importante: los datos son locales
  • Los datos de Mike en su PC no son los mismos que en su celular. Son localStorage separados.
  • Si un tercero abre la URL de GitHub Pages, empieza con los datos de Mike precargados en el código (el estado inicial), no con los datos actuales de Mike.
  • Para datos compartidos en tiempo real entre dispositivos habría que agregar una base de datos en la nube —lo cual aumentaría mucho la complejidad.

Fase 2 — Construcción

⚡ Hacer que los clicks funcionen: Event Delegation

Acá está la explicación del bug que tenía la primera versión: "no funciona cuando clickeo en los números". Este es un problema clásico de JavaScript y vale la pena entenderlo porque ilustra perfectamente cómo piensan los programadores.

La primera versión usaba inline event handlers (manejadores de eventos en línea): cada botón tenía su propia instrucción onclick="toggle(...)" escrita directamente en el HTML. En algunos navegadores esto falla por problemas de scope (contexto de ejecución).

La solución fue event delegation: en vez de que cada uno de los 1.000+ botones escuche sus propios clicks, un único "recepcionista" en el contenedor padre escucha todos los clicks y determina en cuál botón ocurrieron.

Conceptos clave
Event / Event Handler
Evento / Manejador de eventos
Un "evento" es cualquier acción del usuario: click, toque, tecla presionada. Un "event handler" es la función JavaScript que responde a ese evento. Sin event handlers, la página no reacciona a nada.
Event Delegation
Delegación de eventos
Técnica donde en vez de asignar un event handler a cada elemento, se asigna uno solo al contenedor padre. Cuando ocurre un click en cualquier hijo, "burbujea" hacia arriba hasta el padre, que lo procesa. Más eficiente y más robusto.
Event Bubbling
Burbujeo de eventos
Cuando hacés click en un elemento, el evento "sube" automáticamente por todos sus elementos padre hasta llegar al <body>. Event delegation aprovecha este comportamiento para escuchar desde un elemento superior.
data-* attributes
Atributos de datos personalizados
Una forma de guardar información directamente en el HTML de un elemento. En la app, cada botón tiene data-sec="MEX" y data-n="6" para que al hacer click sepamos exactamente de qué figurita se trata, sin depender del texto visible.
El antes y el después del bug
❌ VERSIÓN 1 — inline handler (frágil, causaba el bug) <button onclick="toggle('MEX','6')">6</button> // El problema: 'toggle' no siempre está disponible en ese contexto ✅ VERSIÓN 2 — event delegation (robusto) <button data-sec="MEX" data-n="6">6</button> // Un solo listener en el contenedor maneja TODOS los clicks document.getElementById('cards').addEventListener('click', function(e) { const btn = e.target.closest('[data-n]'); // ¿qué botón fue? if (!btn) return; const secId = btn.dataset.sec; // "MEX" const n = btn.dataset.n; // "6" counts[secId][n]++; // suma 1 al contador });
🏨
La analogía Imaginá un hotel con 1.000 habitaciones. La versión 1 era poner un empleado detrás de cada puerta esperando que llamen. La versión 2 es poner una recepcionista en el lobby: todos los huéspedes pasan por ella, y ella sabe exactamente a qué habitación va cada uno leyendo la llave (los atributos data-*).

👥 Sistema de múltiples usuarios (Perfiles)

Cuando pediste "más de un usuario", la pregunta técnica fue: ¿cómo guardo datos separados para cada perfil usando solo localStorage, que es un único espacio de almacenamiento por sitio?

La solución es conceptualmente simple: usar diferentes "llaves" (keys) en localStorage para cada usuario. Es como tener varios cajones en un mismo mueble, uno por persona.

Conceptos clave
Key-Value Store
Almacén de clave-valor
Una forma de guardar datos donde cada pieza de información tiene un nombre único (clave) y un contenido (valor). localStorage es un key-value store. Es como un diccionario: buscás por palabra y obtenés la definición.
State Management
Gestión de estado
Cómo una app recuerda y gestiona la información "activa" en un momento dado: quién es el usuario actual, qué figuritas tiene, qué filtro está activado. El "estado" es la fotografía completa de la app en un instante.
Hardcoded data
Datos incrustados en el código
Cuando un valor se escribe directamente en el código en lugar de venir de una base de datos o configuración externa. Los datos iniciales de Mike (sus 774 figuritas) están hardcodeados: están escritos en el archivo .html.
Cómo se separan los datos por usuario
// Las "llaves" en localStorage para cada usuario: "figus26-data-Mike" → { MEX: {1:1, 6:0, ...}, ARG: {...} } "figus26-data-FLM" → { MEX: {1:0, 6:0, ...}, ARG: {...} } "figus26-users" → [{id:"Mike",name:"Mike"}, {id:"FLM",name:"FLM"}] "figus26-active" → "Mike" // quién está activo ahora // Cuando cambiás de perfil: 1. Guardo los datos del usuario actual (save()) 2. Cambio el usuario activo en localStorage 3. Leo los datos del nuevo usuario 4. Re-dibujo toda la pantalla con los nuevos datos
📁
La analogía Es exactamente como tener distintos perfiles en Netflix. El contenido (la plataforma) es el mismo para todos, pero cada perfil tiene su propio historial, preferencias y configuración. Acá, la "plataforma" es el archivo HTML y cada perfil guarda su propio estado del álbum.
Lo que hice en este paso
  • Creé los perfiles por defecto: Mike (con sus 774 figuritas pre-cargadas) y FLM (álbum vacío)
  • Los datos de Mike están hardcoded en el código: si alguien abre la URL de GitHub Pages, ve el estado inicial de Mike, no su estado actual
  • Los cambios posteriores de cada usuario se guardan en su propio espacio de localStorage, en el dispositivo donde usa la app

📤 Exportar e Imprimir: APIs del navegador

El botón "Exportar texto" y el botón "Imprimir" parecen simples, pero usan dos tecnologías distintas que vale la pena entender.

Para exportar, usamos la Clipboard API: le pedimos al navegador que copie texto al portapapeles del sistema operativo. Para imprimir, usamos CSS de impresión (@media print): un conjunto de estilos especiales que solo se activan cuando el navegador va a imprimir, transformando radicalmente el diseño para que entre todo en una hoja A4.

Conceptos clave
API — Application Programming Interface
Interfaz de Programación de Aplicaciones
Un conjunto de "puertas de acceso" que un sistema ofrece para que otros programas interactúen con él. El navegador expone APIs para todo: el portapapeles, la geolocalización, la cámara, el almacenamiento. La Clipboard API da acceso al copy/paste del sistema.
@media print
Regla de medios para impresión
Una instrucción CSS que dice "estas reglas solo aplican cuando se está imprimiendo". Permite tener un diseño completamente diferente para la pantalla y para el papel: fuentes más chicas, sin botones, layout en columnas, colores distintos.
CSS Columns
Columnas CSS
Una propiedad CSS que distribuye el contenido automáticamente en múltiples columnas, como un periódico. Se usó para el layout de impresión: todos los equipos se distribuyen en 3 columnas para entrar en una hoja A4.

Fase 3 — Publicación

🌐 Publicar en internet: GitHub y GitHub Pages

Tener el archivo en tu PC está bien, pero para que "un tercero lo vea desde un celular" necesitamos que esté en un servidor en internet. Ahí entraron GitHub y GitHub Pages.

Encontré que tu PC tenía credenciales de GitHub guardadas (de una sesión anterior). Con esas credenciales, usé la API de GitHub para crear un repositorio, subir el archivo y activar el hosting —todo automáticamente, sin que vos tocaras nada.

Conceptos clave
Git
Git (sin traducción)
Sistema de control de versiones: registra cada cambio que se hace en archivos de código, quién lo hizo y cuándo. Es como el historial de versiones de Google Docs pero para código. Creado por Linus Torvalds (el mismo de Linux) en 2005.
GitHub
GitHub (sin traducción)
Plataforma web para guardar proyectos de código con Git. Es la "nube" del mundo del desarrollo. Más de 100 millones de desarrolladores guardan ahí su código. Fue comprada por Microsoft en 2018 por 7.500 millones de dólares.
Repository / Repo
Repositorio
Una carpeta en GitHub que contiene el código de un proyecto, con todo su historial de cambios. Como una carpeta en Drive pero con superpoderes: historial completo, quién cambió qué y cuándo, posibilidad de volver a cualquier versión.
GitHub Pages
Páginas de GitHub
Un servicio gratuito de GitHub que toma los archivos de un repositorio y los sirve como un sitio web. En menos de 2 minutos, tu repositorio se convierte en una URL pública. Perfecto para sitios estáticos.
Token / OAuth Token
Token / Credencial de acceso
Una contraseña temporal y revocable que da acceso a una API. En vez de usar tu contraseña real, los servicios generan tokens con permisos específicos y fecha de vencimiento. Más seguro que compartir la contraseña directamente.
API REST — HTTP Methods
API REST — Métodos HTTP
Protocolo para que programas se comuniquen via internet. Los "métodos" son tipos de pedidos: GET (traer), POST (crear), PUT (actualizar), DELETE (borrar). Para subir el archivo usé un PUT a la API de GitHub.
Base64 encoding
Codificación en Base64
Una forma de convertir archivos binarios (o texto) en una cadena de caracteres que se puede enviar de forma segura por cualquier canal de texto (como una API). El archivo HTML se convirtió a Base64 antes de enviarlo a GitHub.
Deploy / Deployment
Despliegue
El proceso de poner una aplicación en producción: subirla al servidor donde va a funcionar de forma pública. En este caso, el deploy fue subir el archivo a GitHub y activar Pages. El "depliegue" tardó menos de 2 minutos.

Lo que hice paso a paso
  • Verificación: encontré credenciales de GitHub guardadas en el administrador de credenciales de Windows (credential manager). El usuario es miguelippolito3-cloud.
  • Creación del repo: HTTP POST a la API de GitHub → nuevo repo público llamado "figus-mundial-2026".
  • Upload del archivo: convertí index.html a Base64 con Python y lo subí via HTTP PUT a la API de contenidos de GitHub.
  • Activación de Pages: HTTP POST a la API de GitHub Pages → indicando que sirva desde la rama "main", directorio raíz.
  • Verificación: consulté el estado cada 15 segundos hasta que Pages reportó "built" (construido). Tardó ~45 segundos.

🎓 Lo que construimos y lo que aprendiste

En una sola sesión, partiendo de fotos y una descripción en lenguaje natural, construimos una aplicación web completa con sistema de usuarios, persistencia de datos, interfaz interactiva, exportación de texto, layout de impresión y publicación en internet. Sin que vos escribieras una sola línea de código.

Esto no es magia. Es la combinación de décadas de tecnologías bien establecidas (HTML, CSS, JavaScript, Git) con una capa de IA que actúa como el programador que las conecta. Lo que cambia con la IA no es la tecnología de fondo —esa es la misma de siempre— sino quién puede acceder a ella.

🌐 El navegador es poderoso HTML + CSS + JS pueden construir apps muy sofisticadas sin instalar nada. El navegador moderno es un entorno de ejecución completo.
💾 Los datos viven en el dispositivo localStorage guarda todo localmente. Para datos compartidos entre personas habría que agregar un servidor —eso es el siguiente nivel de complejidad.
🐛 Los bugs son normales y tienen causa El bug del click no fue un error aleatorio: tenía una causa técnica precisa (inline handlers vs event delegation). Entender el porqué de un bug es más valioso que el fix.
🚀 GitHub Pages = hosting gratuito instantáneo Para sitios estáticos, GitHub Pages es imbatible: gratuito, confiable, rápido y se actualiza automáticamente con cada cambio.
🤖 La IA amplifica, no reemplaza Vos aportaste el problema, el criterio y la validación. Yo aporté la ejecución técnica. El resultado es mejor que lo que cualquiera de los dos hubiera hecho solo.
🔑 El prompt es la habilidad clave La calidad de lo que construimos dependió en gran medida de qué tan bien describiste el problema, mostraste ejemplos y fuiste específico en los formatos que querías.
